# 工具知識編譯器（Wiki Compiler）

> 新增於 2026-09-20。本文檔說明新的「工具解析邏輯」與「工具配對邏輯」。
> 統計數字以撰寫當下的評測集 v1.2.0（169 筆）為準，重跑後請更新。

## 1. 啟發：從「檢索器」升級成「知識編譯器」

LLM Wiki 的核心主張是：**不要每次查詢都重新讀原始素材，而是離線先把
原始素材編譯成結構化詞條**，查詢時直接查編譯好的詞條。
Graphify 那類知識圖譜工具補上第二件事：把素材裡的**關係**也抽出來建成圖，
查詢時沿著圖擴散，就能找到字面上沒出現、但概念上相連的東西。

這兩件事搬到本專案，剛好對應到一個已診斷清楚、但一直解不掉的洞。

## 2. 要解決的洞：詞彙鴻溝

`npm run ceiling` 長期顯示 semantic 類型天花板只有約 91%。逐題詞彙重疊分析後
確認根因**不是**「metadata 太薄」（全庫 547/705 描述短於 60 字，短描述是常態），
而是兩邊在講不同的語言：

| | 語言 | 例子 |
|---|---|---|
| 使用者查詢 | 日常語言、具體應用情境 | 「齒輪的齒數跟模數一改整組尺寸自動跟著變」 |
| 工具 metadata | 技術分類、通用能力 | 「參數化 3D CAD 腳本框架」 |

兩者 bigram **重疊為 0**。純詞彙檢索（四維引擎就是）在原理上不可能找到。

先前試過的解法都失敗：
- **embedding**：該 API 端點沒有 embedding 模型可用。
- **HyDE 查詢改寫**：每次查詢都要呼叫 LLM（+6s），增益落在雜訊內，不採用。

## 3. 新架構

```
        ── 離線（跑一次）──                        ── 查詢時 ──
registry/tools.json                              使用者查詢
        │                                              │
        ▼                                              ▼
scripts/compile-wiki.js ──► registry/compiled-entries.json
  （解析邏輯：編譯器）          （編譯好的知識詞條）         │
                                       │                  │
                                       ▼                  ▼
                              core/wiki-matcher.js ──► V5 維度
                              （配對邏輯）                 │
                                                          ▼
                                          core/agent-retrieval.js（五維融合）
```

### 3.1 解析邏輯：`scripts/compile-wiki.js`

把每支工具的 metadata 編譯成**查詢導向**的詞條：

```json
{
  "cadquery": {
    "intents":     ["齒輪的齒數改了整組尺寸要自動跟著變", "用程式碼畫出可以改參數的 3D 零件"],
    "objects":     ["3D 模型", "STEP", "STL"],
    "actions":     ["建模", "參數化"],
    "constraints": ["Python"],
    "negative":    [],
    "tier": 1
  }
}
```

`intents` 是關鍵——它是「使用者會怎麼開口」，不是「工具是什麼」。

兩個層級：

| 層級 | 指令 | 需要 API | 說明 |
|---|---|---|---|
| Tier 0 | `--offline` | 否 | 規則式：把既有結構化欄位（useCase_zh / triggers / negativeConstraints_zh）重組為詞條 |
| Tier 1 | 預設 | 是（AGNES_API_KEY） | LLM 語意編譯：產生使用者語言的應用情境句 |

Tier 0 沒有語意增益，但讓整條管線在沒有 key 時也能跑、能測、能驗證零回歸。
Tier 1 覆寫 `intents`，其餘欄位保留 Tier 0 的內容。

### 3.2 配對邏輯：`core/wiki-matcher.js`

查詢時比對的是**編譯好的詞條**，不是原始描述。三個訊號取最大值
（沿用四維引擎「取最佳維度」的哲學）：

| 訊號 | 說明 |
|---|---|
| V5a `intent` | 查詢詞袋 vs 詞條詞袋（IDF 加權餘弦），直接比對 |
| V5b `graph` | 知識圖譜一階擴散後再比一次 |
| V5c `facet` | 比對 objects + actions（短詞、鑑別力高） |

**知識圖譜**是「詞—詞共現圖」：兩個詞若同時出現在 ≥ 3 支工具的 intents 中
就連一條邊。查詢時把查詢詞的鄰居詞以 0.6 的衰減權重加進詞袋再比一次。
只做一階，不做二階以上——擴散越深雜訊爆炸得越快。

### 3.3 與 HyDE 的關鍵差別

| | HyDE | 知識編譯器 |
|---|---|---|
| LLM 呼叫時機 | 每次查詢 | 705 支工具跑一次 |
| 查詢延遲 | +6s | 0（只查本地詞檔） |
| 實測結果 | 不採用 | 見 §5 |

這是「一次編譯、永久受用」對上「每次重算」的差別。

## 4. 兩個防護（都是本專案踩過的坑）

1. **萬能詞黑名單**：LLM 會產生「幫我處理資料」這種任何工具都適用的句子，
   寫進去任何查詢都會命中。判準是「有沒有具體對象」——
   「幫我畫圖」放行，「幫我搞定」擋掉。（沿用 `enrich-triggers-llm.js` 的教訓）
2. **鑑別力守門**：一句 intent 若**沒有任何一個詞具有鑑別力**
   （所有詞的 df 都 > 6% × N），代表它是空話 → 剔除。
   這是 trigger 擴充「擴到 361 筆反而退步 11.9% → 7.1%」的教訓。
3. **簡繁校正**：所有產出都過 `toTraditional()`。
   這不是多此一舉——繁體查詢**永遠匹配不到簡體詞**
   （bigram 零重疊），而 LLM 輸出簡體的比例不低。
   ⚠️ 2026-09-20 在此發現 `toTraditional()` 本身有循環盲區
   （見 `HANDOFF.md` 陷阱 19），已修復。

|---|---|---|---|

| ├ direct | 100.0% | 100.0% | — |
| ├ semantic | 91.1% | **93.7%** | +2.6pp |
| └ constrained | 96.9% | **100.0%** | +3.1pp |
| constrained 平均排名 | 35.2 | **4.7** | 大幅改善 |
| top1 命中 | 51.6% | **59.7%** | +8.1pp |

| 空集誠實率 | 100%（10/10）| **100%（10/10）** | 未引入偽陽性 |

| | V5 停用 | V5 啟用 |
|---|---|---|
| top-10 | 86.2% | **88.1%** |
| top-20（rerank 天花板）| 89.3% | **90.6%** |

### 5.3 rerank 路徑：沒有顯著變化 ⚠️

實測（`npm run eval:rerank`，需 API，每輪約 10~13 分鐘）：

| 組別 | 嚴格 Hit@1 | 成功呼叫 |
|---|---|---|
| V5 啟用 Run 1 | 79.9% | 157 |
| V5 啟用 Run 2 | 78.0% | 158 |
| V5 啟用 Run 3 | 78.0% | 156 |
| V5 啟用平均 | **78.6%** | — |
| V5 停用（本日末輪） | 73.0% | 153 |
| V5 停用（導入前歷史值） | 79.2% | — |

🔴 **這組數字不能拿來下結論**。停用組的 73.0% 是在連續四輪評測之後才跑的，
命中本專案記錄過的**配額遞減順序效應**：先跑的佔到新鮮配額，後跑的失敗數變多
（成功呼叫 153 vs 156~158，失敗時 rerank 被略過、退回融合排序，分數自然偏低）。

→ 保守結論：**rerank 路徑沒有可證實的變化**（最可能是中性）。
→ 若要定論，必須做**交替配對 A/B**（同一批查詢內 V5 開／關交錯），
   不能用「先跑三輪 A、再跑一輪 B」的順序設計。

原因推測：rerank 的瓶頸是 **LLM 的挑選力**，不是候選池。
候選池確實變好了（top-20 天花板 89.3% → 90.6%），
但 LLM 在有答案的候選中挑對的比例沒有提升（約 88.7% → 87.2%，雜訊內）。
這與既有的結論一致：`core/llm-rerank.js` 註解裡的「瓶頸在挑選力而非召回」。

→ **V5 的價值在詞彙／融合路徑（快速搜尋，+8pp，確定性）**，
   深度搜尋（rerank）不受影響也不受損。

### 5.5 權重消融：為什麼 Tier 0 是 0.10、Tier 1 是 0.20

| V5 權重 | 天花板 | 平均排名 | top1 |
|---|---|---|---|
| 停用 | 95.0% | 54.4 | 51.6% |
| **0.10** | **95.6%** | **48.1** | **54.7%** |
| 0.15 | 94.3% | 60.2 | 55.3% |
| 0.20 | 93.7% | 66.8 | 52.2% |
| 0.25 | 93.1% | 73.2 | 52.2% |
| 0.15 無圖譜 | 93.7% | 66.3 | 55.3% |

**Tier 0** 趨勢單調：V5 給越多，天花板掉越多（擠壓 V1~V4 的召回貢獻），
0.10 是唯一「天花板不降反升」的設定。
另：0.15 有圖譜 vs 無圖譜（94.3% / 60.2 vs 93.7% / 66.3）顯示**圖譜擴散在 Tier 0 有貢獻**。

**Tier 1（現行）**則完全不同——天花板在 0.10~0.40 之間都維持 96.9%，不再隨權重下降：

| V5 權重 | 天花板 | 平均排名 | top1 |
|---|---|---|---|
| 停用 | 95.0% | 54.5 | 51.6% |
| 0.10 | 96.9% | 35.6 | 55.3% |
| 0.15 | 96.9% | 35.4 | 57.9% |
| **0.20** | **96.9%** | **35.4** | **59.7%** |
| 0.25 | 96.2% | 41.2 | 60.4% |
| 0.30 | 96.9% | 35.4 | 58.5% |
| 0.40 | 96.9% | 35.8 | 55.3% |

🔴 **「加權重天花板就掉」不是通則**：差別在於詞檔品質。
Tier 0 詞條沒有召回力，權重越大越排擠 V1~V4；
Tier 1 詞條本身就能召回，加權不會犧牲原四維。
→ **每次重新編譯詞檔都要重跑 `npm run ablate:v5`**，最適值會跟著詞檔變。

⚠️ 附帶發現：**知識圖譜在 Tier 1 下幾乎無貢獻**
（w=0.20 有圖譜 59.7% vs 無圖譜 59.7%，完全相同）。
原因是圖譜密度從 Tier 0 的 789 節點/1151 邊降到 355/264——
LLM 句子太多元，詞對共現達不到 `MIN_COOC=3`。

### 5.6 零回歸保證

V5 權重從 V1~V4 等比挪過來（V1~V4 = 原始比例 × 0.8），
所以「詞檔不存在」或「詞檔全部無關」時，V1~V4 的相對大小完全不變 →
排序必然不變。這條性質有單元測試鎖住
（`tests/wiki-matcher.test.js`：詞檔無關時排序與無詞檔完全一致）。

## 6. 使用方式

```bash
# Tier 0：規則式編譯（不需 API key）
npm run compile:wiki -- --offline

# Tier 1：LLM 語意編譯（需要 AGNES_API_KEY，可續跑）
AGNES_API_KEY=sk-... npm run compile:wiki -- --limit=10 --dry   # 先看 prompt
AGNES_API_KEY=sk-... npm run compile:wiki -- --limit=30
AGNES_API_KEY=sk-... npm run compile:wiki                        # 全量 705 筆

# 只看覆蓋率與圖譜統計
npm run compile:wiki -- --stats

# 權重消融（確定性、不需 API）：每次重新編譯詞檔後都該重跑
npm run ablate:v5
npm run ablate:v5 -- --weights=0.05,0.10,0.15
```

⚠️ **換詞檔就要重跑消融**：V5 的最適權重取決於詞檔內容，
Tier 0 的最佳值（0.10）在 Tier 1 之後未必一樣。
`scripts/v5-ablate.js` 會直接印出建議值，記得寫回
`core/agent-retrieval.js` 的 `V5_WEIGHT` 與 `DIM_WEIGHTS`。

其他參數：`--ids=a,b,c`（只編譯指定工具）、`--batch=3`、
`--model=agnes-2.5-flash`、`COMPILE_CONCURRENCY=2`（並行數，429 限流嚴重）。
