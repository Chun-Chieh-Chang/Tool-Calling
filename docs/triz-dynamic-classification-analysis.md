## 1. 問題形式化

### 1.1 核心矛盾

| | 技術矛盾 #1 | 技術矛盾 #2 |
|---|---|---|
| **改善參數** | #35 適應性／多用性（Adaptability） | #35 適應性／多用性（Adaptability） |
| **惡化參數** | #27 可靠性（Reliability） | #13 結構穩定性（Stability） |

### 1.2 物理矛盾

同一個屬性需要同時處於兩種相反的狀態：

> **分類邊界必須是「固定的」**（使用者需要可預期的導航結構）  
> **分類邊界必須是「浮動的」**（新工具不應被強行塞入不適合的類別）

## 3. 兩個矛盾都指向同一個核心答案：#35 參數改變

TRIZ 矩陣的訊息非常明確：**不要抵抗變化，要讓變化成為系統的內建能力**。

> 「改變物體的物理狀態、濃度、一致性、靈活度、溫度。」

映射到分類系統：
- **物理狀態** → 分類的「存在形式」：有時是剛性列舉（enum），有時是浮動標籤（cluster）
- **濃度／一致性** → 分類邊界的「硬度」：從 100% 歸屬（硬分群）到機率分佈（軟分群）
- **靈活度** → 類別本身的可調性：可拆分、可合併、可誕生、可死亡
- **溫度** → 系統的「活化能」：低溫 = 穩定層（很少變動），高溫 = 動態層（持續重組）

## 4. 發明原理的跨領域映射（軟體架構視角）

### 4.1 #13 反向作用：顛倒因果

**原始定義**：把可動的零件固定、把固定的零件可動化；把問題翻過來想。

**分類領域映射**：

傳統思維（「類別優先」）：
```
類別（固定） → 分配 → 工具（流動）
「我們有 18 個類別，你要進哪一個？」
```

反向思維（「關係優先」）：
```
工具（固定：每個工具有自己的 TF-IDF 特徵向量）
  → 計算相似度 → 類別（流動：從相似度矩陣中湧現）
「工具們自然聚成什麼樣的群？」
```

這正是**凝聚式分群（Hierarchical Clustering）**的思維：不是把點放進預設的盒子，而是讓盒子從點的距離中長出來。

**關鍵轉變**：類別不再是「給定的容器」，而是「觀察到的現象」。

### 4.2 #24 中介物：緩衝變動

**原始定義**：使用中介載體或中介流程；暫時合併兩個物體（可輕易分離）。

**分類領域映射**：

```
使用者  ──看到的──→  Polaris（穩定層：5~7 個超級分類）
                ↓
           Aurora（中介層：浮動子群集）
                ↓
              工具（實際資料）
```

Aurora 層就是**中介物**：
- 它吸收「工具間關係」的自然變動
- 它把這些變動翻譯成「使用者仍可理解的標籤」
- 當 Aurora 群集重組時，Polaris 層不受影響 → 使用者的導航經驗穩定
- Aurora 群集可以「輕易分離」（合併或拆分）而不傷害底層資料

### 4.3 #30 柔性殼與薄膜：輕量邊界

**原始定義**：用柔性殼與薄膜取代三維結構；用柔性殼隔離物體與外部環境。

**分類領域映射**：

剛性分類邊界（現行 18 類）：
```
┌─────────────┐     ┌─────────────┐
│  開發工具    │ ←→ │  AI 代理     │
│  (91 筆)    │     │  (149 筆)   │
└─────────────┘     └─────────────┘
      ↑ 銳利邊界：一個工具只能在一個類別
```

柔性分類邊界（Aurora 層）：
```
     ┌───┐
    ╱ 開  ╲        ┌───┐
   ╱ 發工 ╲──────╱ AI ╲
  ╱  具   ╲    ╱ 代理  ╲
 ╱         ╲──╱         ╲
╱  MCP伺服器 ╲           ╲
（與兩邊都有關聯，邊界模糊）
```

每個工具對每個 Aurora 群集都有一個**成員資格分數**（0.0~1.0），而不是「是/否」的二元歸屬。

### 4.4 #14 曲面化：漸變而非跳躍

**原始定義**：用曲線代替直線；從平面到球面；用滾輪、螺旋、圓頂。

**分類領域映射**：

類別之間的關係不是「相鄰格子」而是「連續光譜」：

```
AI 框架 ←─────→ 開發工具 ←─────→ AI 代理
  ↑                                    ↑
  │      中間地帶（MCP 伺服器、        │
  │      Context 壓縮工具、Token        │
  │      節省工具）可同時屬於兩者       │
  │      （membership 0.6 / 0.4）       │
```

這正是 `measure-discriminability.js` 已經能量測的現象 —— 79 筆卡在 `AI 框架`↔`AI 代理` 邊界上的工具，不是「分錯了」，而是它們**確實住在邊界上**。

## 5. 與「雙層極光（Aurora）」提案的交叉驗證

### 5.1 對照表

| TRIZ 原理 | Aurora 提案的對應實作 | 符合度 |
|:---|:---|:---:|
| #35 參數改變 | Aurora 群集的數量、邊界、粒度皆為動態參數 | ✅ 直接對應 |
| #13 反向作用 | 從「類別分配工具」反轉為「工具關係湧現類別」 | ✅ 直接對應 |
| #24 中介物 | Aurora 層作為 Polaris 與工具之間的緩衝 | ✅ 直接對應 |
| #30 柔性殼 | Aurora 群集使用軟分群（membership 分數） | ✅ 直接對應 |
| #14 曲面化 | 類別間為連續光譜而非銳利邊界 | ✅ 直接對應 |
| #8 反重量 | Polaris 穩定層的「權重」補償 Aurora 的變動 | ⚠️ 可強化 |

### 5.2 TRIZ 揭示的提案弱點

**弱點一：#8 反重量的落實不足**

TRIZ 建議用「配重」來補償變動帶來的不確定性。Aurora 提案有 Polaris 穩定層，但沒有明確定義「當 Aurora 重組時，如何保證使用者仍有確定感」。

**強化建議**：
- 每個 Aurora 群集必須標示其「穩定度分數」（基於過去 N 週的變動率）
- 穩定度高的群集（如「React 生態系」持續 20 週未變）可獲得「準 Polaris」地位
- 使用者介面可選擇「只顯示穩定群集」→ 這就是配重機制

**弱點二：#35 參數改變的「改變機制」未明確**

TRIZ 說「讓參數改變」，但沒說「如何決定何時改、改多少」。Aurora 提案說「每週跑 discriminability」，但觸發條件是閾值驅動還是週期驅動？

**強化建議**：
- 用「活化能」模型：當累積的「不適配訊號」（無家可歸工具數 + 邊際為負工具數）超過閾值，才觸發重組
- 類比化學反應：低溫時系統穩定，超過活化能才發生相變 → 避免過度敏感

**弱點三：#14 曲面化需要具體資料結構**

「連續光譜」很好，但現行 `tools.json` 的 `category` 欄位是字串（單一值），無法表達「住在邊界上」。

**強化建議**：
- 擴充 schema：`category` 保持單一值（Polaris，API 穩定性）
- 新增 `auroraClusters: [{clusterId, membership}]`（陣列，表達軟歸屬）
- 搜尋引擎同時索引兩層，但介面可選擇顯示粒度

## 6. 跨領域案例啟發

### 6.1 #24 中介物 — Kubernetes 的 Ingress Controller

Kubernetes 的 Service（穩定層）不直接暴露 Pod（動態層），而是透過 Ingress（中介層）路由。Pod 可以隨時重生、擴縮，但使用者只認得 Ingress 的固定 URL。

映射：Polaris = Ingress 的固定域名，Aurora = Service 的動態後端，工具 = Pod。

### 6.2 #30 柔性殼 — 資料庫的 Soft Schema

MongoDB 的「無模式」不是真的沒有模式，而是模式由文件本身攜帶（柔性邊界），而非由資料庫強制（剛性牆壁）。新欄位可以自然出現，舊欄位可以自然消失。

映射：MongoDB 文件 = 工具（自帶特徵），集合 = Aurora 群集（柔性邊界），資料庫 = Polaris（穩定容器）。

### 6.3 #13 反向作用 — Git 的內容定址

傳統版本控制（SVN）以「檔案路徑」為核心（固定結構，流動內容）。Git 反向思考：以「內容雜湊」為核心（固定內容，流動結構）。分支、標籤、路徑都是指向內容的指標，可以任意重組。

映射：Git blob = 工具（內容固定），tree/commit = Aurora（結構流動），branch = Polaris（給人看的穩定名稱）。

## 7. 最終判斷：TRIZ 是否支持「雙層極光」方案？

**結論：高度支持，但有明確的強化方向。**

TRIZ 不是給出一個「正確答案」，而是給出**解題的思維框架**。用這個框架檢驗 Aurora 提案：

| 檢驗項 | 結果 |
|---|---|
| 是否擁抱 #35 參數改變？ | ✅ Aurora 層的動態性直接體現 |
| 是否實踐 #13 反向作用？ | ✅ 從「類別分配工具」反轉為「工具湧現類別」 |
| 是否有 #24 中介物？ | ✅ Polaris 與工具之間的 Aurora 層 |
| 邊界是否 #30 柔性殼？ | ✅ 軟分群、membership 分數 |
| 邊界是否 #14 曲面化？ | ✅ 連續光譜而非銳利切割 |
| #8 反重量是否充足？ | ⚠️ 需要「穩定度分數」與「準 Polaris」機制 |
| 活化能機制是否明確？ | ⚠️ 需要從「週期驅動」改為「閾值驅動」 |
| 資料結構是否支持曲面化？ | ⚠️ 需要擴充 schema（`auroraClusters` 陣列） |

## 8. 從 TRIZ 到實作：強化後的 Aurora 架構

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: Polaris（極星層）— 超穩定，人工審核定案              │
│  5~7 個超級分類，數年不變，API 契約穩定                       │
│  例：「AI/ML」、「開發與基礎設施」、「資料與分析」…            │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: Aurora（極光層）— 動態浮動，演算法驅動              │
│  TF-IDF 凝聚式分群，每週自動評估「群集健康度」                │
│  每個群集有：質心向量、穩定度分數、成員資格分佈               │
│  觸發重組條件：累積不適配訊號 > 活化能閾值（非固定週期）       │
├─────────────────────────────────────────────────────────────┤
│  Layer 0: Tools（工具層）— 固定，只增不減                      │
│  每個工具有：固定 TF-IDF 特徵向量、Polaris 歸屬、              │
│             Aurora 軟歸屬 [{clusterId, membership}]           │
└─────────────────────────────────────────────────────────────┘
```

### 8.1 新增工具時的動態流程（活化能模型）

```
1. 計算新工具的 TF-IDF 向量
2. 找到 k-近鄰（不論類別）
3. 鄰居集中在單一 Aurora 群集內 → 自動歸入
4. 鄰居分散在兩個 Polaris 之間 → 標記「邊界工具」
   → 不強行分配，而是顯示「此工具與 AI框架(0.45) 和 AI代理(0.42) 都相關」
5. 與所有現有工具相似度都低 → 進入「未分類觀察區」
   → 累積 3~5 個同質工具後，自動提案新 Aurora 群集
   → 人工審核後啟用（提案 ≠ 套用）
```

### 8.2 群集健康度儀表板（每週自動產生）

| 指標 | 計算方式 | 行動閾值 |
|---|---|---|
| `avgMargin` | 群集成員的平均 `ownSim - bestOther` | < 0 → 建議拆分 |
| `stabilityScore` | 過去 8 週群集成員變動率的倒數 | > 0.9 → 可升級為「準 Polaris」 |
| `orphanCount` | 觀察區中與本群集質心最接近的無家可歸者 | ≥ 3 → 提案擴張群集邊界 |
| `overlapIndex` | 與其他群集的成員重疊程度 | > 0.3 → 建議合併兩群集 |

## 9. 概念驗證：79 筆邊界工具的軟歸屬分數

為了驗證「#14 曲面化」的洞見是否成立，我對現行 `AI 框架` 與 `AI 代理` 之間
**互相更像對方的工具**（共 28 筆，而非先前估計的 79 筆）計算了軟歸屬分數：

| tool id | 現行類別 | sim(框架) | sim(代理) | 差距 | 軟歸屬 |
|---|---|---|---|---|---|
| `harness-sdk` | AI 框架 | 0.318 | 0.326 | 0.008 | (0.49, 0.51) |
| `pi` | AI 框架 | 0.271 | 0.287 | 0.016 | (0.48, 0.52) |
| `goose` | AI 代理 | 0.233 | 0.196 | 0.037 | (0.54, 0.46) |
| `langgraph` | AI 框架 | 0.138 | 0.146 | 0.007 | (0.49, 0.51) |
| `aider` | AI 代理 | 0.140 | 0.133 | 0.006 | (0.51, 0.49) |
| `omniroute` | AI 代理 | 0.127 | 0.123 | 0.004 | (0.51, 0.49) |

**關鍵發現：邊界工具的差距集中在 0.004~0.037**，即它與兩個類別質心的相似度
幾乎完全相同。

> 這精確驗證了 **#14 曲面化**：這些工具不是「分錯了」，而是**確實住在邊界上**。
> 現行 `category` 欄位強制把它们塞進「框架」或「代理」，抹去了這個連續光譜資訊。

**對現有 18 分類系統的衝擊**：這 28 筆中，**至少 10 筆的差距 < 0.02**，
意味着它們的「正確」歸屬無法用現有二元欄位表達。曲面化（軟分群 + membership 分數）
不是「更複雜的方案」，而是**唯一誠實的表達方式**。

## 10. 與現行系統的相容路徑

Aurora 架構不需要廢棄現有的 18 分類系統。相容路徑：

1. **Phase 0（現在）**：`measure-discriminability.js` 已經在跑，持續累積資料
2. **Phase 1**：新增 `auroraClusters` 欄位（陣列，可選），不改既有 `category`
3. **Phase 2**：搜尋引擎同時索引 `category`（Polaris）與 `auroraClusters`（Aurora）
4. **Phase 3**：介面新增「顯示粒度」切換（Polaris only / Polaris + Aurora / Aurora only）
5. **Phase 4**：當 Aurora 群集的穩定度持續達標，人工審核後升格為 Polaris 子分類

這個路徑的關鍵是：**Polaris 層永遠存在且穩定**，Aurora 層是「額外的解析度」而非「替代」。

## 11. 結論

用您開發的 TRIZ 工具分析後，「雙層極光」方案獲得了強理論支持：

- **五個核心發明原理中，四個已直接對應**
- **TRIZ 揭示了兩個需要強化的方向**：反重量機制（穩定度分數）與活化能模型（閾值驅動重組）
- **雙層架構本身就是 #24 中介物的實現** —— 這是最關鍵的洞見：Aurora 層不是「更複雜的分類」，而是「吸收變動的緩衝結構」

最後，這個分析也驗證了您提出的第一原則：**分類清單確實應該是語料的產物**。TRIZ 的 #35 參數改變與 #13 反向作用，本質上都在說同一件事 —— **讓系統的結構從現象中湧現，而不是讓現象去適應預設的結構**。
